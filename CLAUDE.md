## 1. Commands

All commands are Melos-scoped and run from the repo root (FVM-managed Flutter, see `.fvmrc`).

| Task | Command |
|------|---------|
| Bootstrap workspace (link all packages) | `melos run refresh` (or `melos bootstrap`) |
| Install deps after pubspec changes | `melos run get` |
| Codegen (Drift, JsonSerializable, build_runner) | `melos run generate` |
| Drift migration generation | `melos run generate:migration` |
| Lint / analyze all packages | `melos run analyze` |
| Run all tests (all packages) | `melos run test` |
| Run a single test | `fvm flutter test test/<file>_test.dart` (from the module dir) |
| Run the app | `fvm flutter run` |
| Merged coverage report (lcov + cobertura) | `melos run coverage:merged` (open with `coverage:merged:open`) |

Notes:
- Run `melos run generate` after modifying any table, model, or API interface to refresh `*.g.dart` files. `*.g.dart` is excluded from analysis in `analysis_options.yaml`.
- After adding a new module or changing a package's deps, run `melos run refresh` — it cleans, bootstraps, and re-links the whole workspace.
- Lint rules enforced globally via `analysis_options.yaml`: strict trailing commas (`require_trailing_commas`), relative imports within a package (`prefer_relative_imports`), single quotes, grouped/sorted imports (`directives_ordering`), and mandatory declared return types (`always_declare_return_types`).

## 2. Tech Stack & Environment

- **Linting**: Rules enforced via `analysis_options.yaml` (see §1).

## 3. Architecture & Directory Structure
The project follows a **Modular Clean Architecture** pattern with a sharded directory structure in `module/`:
- **root (`/`)**: Main entry point (`lib/main.dart`) where `WrapperScreen` handles global service registration.
- **`module/entity/`**: Pure data models and value objects (`entity_manga`) plus scraped-source DTOs (`entity_manga_external`).
- **`module/domain/`**: Business logic, use cases, and repository interfaces (`domain_manga`).
- **`module/core/`**: Infrastructure and cross-cutting concerns (Route, Network, Storage, Analytics, Environment). `core_storage` wires the database, DAOs, and caches.
- **`module/library/`**: Internal utility libraries and 3rd-party wrappers (Drift service, Service Locator, BLoC, MangaDex API).
- **`module/ui/`**: Reusable UI components, themes, and shared widgets (`ui_common`). Feature-specific UI modules (e.g., `ui_browse`) contain both Screens and their colocated Cubits.
- **`module/feature/`**: High-level feature orchestration and routing. Bridges UI with Domain and Core; the only layer that knows navigation.

**Big-picture wiring to understand before editing:**
- **Bootstrap order is load-bearing.** `lib/main.dart` → `WrapperScreen` → `locatorBuilder()` runs `locator.reset()`, registers registrars sequentially (CoreAnalytics first, then CoreStorage, CoreNetwork, CoreEnvironment, CoreRoute, DomainManga), then awaits `locator.allReady()`. Circular dependencies between registrars cause startup failures.
- **Registrar/Initiator pattern**: every module exposes a `Registrar` (library modules use the `Initiator` alias) that registers its services into the shared `ServiceLocator` (GetIt-backed). Interfaces are registered via `alias<Interface, Manager>()` — e.g. `PathManager` implements `GetRootPathUseCase`/`GetBackupPathUseCase`/`GetDownloadPathUseCase`.
- **Data flow**: `core_network` (Dio + headless WebView scraping) and `manga_dex_api` (MangaDex REST) feed `domain_manga` use cases, which sync into Drift DAOs (`manga_service_drift` via `core_storage`) and cache managers. UI modules consume use cases via `locator()`, never services directly.
- **Scraping sources**: every non-MangaDex source is a JavaScript file with a `// ==MangaStashSource==` JSON header (`module/domain/domain_manga/assets/sources/*.js`: asura-scans, weeb-central, manga-katana, manhua-plus) defining `const source = {searchUrl, search, manga, chaptersUrl, chapters, images, tagsUrl, tags}`. `ScriptSourceExternal` (implements the `SourceExternal` contract of `entity_manga_external`) runs one function per call through `RunSourceScriptUseCase` (`runOnBlank` for URL builders, `runOnPage` for DOM parsers); `SourceRegistry` (shipped assets + user edits/additions in the DB) resolves sources by name/host, and use cases re-resolve by name so a saved edit applies at once. Selectors are tested with Node under `module/domain/domain_manga/script_test` (`npm ci && npm test`, fixtures in `script_test/fixtures/*`). Mangadex is `builtIn` and goes through `manga_dex_api`; `MangaDexSourceExternal`'s scraping hooks `throw UnimplementedError()` by design.
- **UI convention**: `ui_*` screens are pure widgets that take `onTapX`/`onTapY` callbacks and a static `create(locator:, ...)` factory; `feature_*` route builders supply navigation via `BaseRouteBuilder` (`root()`, `routes()`, aggregated in `lib/main_route.dart`).
- **Gotcha — download is unimplemented**: the "Download" action is a no-op TODO across `ui_browse` and `ui_more`.
- **Web vs IO**: conditional imports select platform implementations (e.g. `PathManager` filesystem adapter — in-memory temp dir on web, app-documents dir on IO; `Executor` in `manga_service_drift`). When DB or path errors appear only on one platform, check the `adapter/` directories.

## 4. Implementation Rules
- **Consistency**: Match existing style and patterns.
- **Code Style**: Single quotes for strings, mandatory trailing commas.
- **Imports**: Grouped (Dart, Package, Relative) and sorted alphabetically. Use relative imports within the same package.
- **Type Safety**: Always declare return types for functions and methods.
- **DI Registration**: Every module MUST provide a Registrar (or Initiator) that registers its services into the ServiceLocator.
- **Generated Code**: Run `melos run generate` after modifying models, tables, or API interfaces to update `.g.dart` files.
- **Result Wrappers**: Network operations (especially in `core_network`) should return a `Result` type (`Success`/`Error`) for explicit error handling.
- **Path Abstraction**: Avoid direct file system access; use `PathManager` or dedicated use cases in `core_storage`.
- **Naming Conventions**: Models in `entity_manga_external` should be suffixed with `Scrapped` to distinguish them from official API entities.
- **Action Delegation**: UI components should delegate navigation and high-level actions via callbacks to remain agnostic of the routing table.
- **Safe BLoC**: Cubits should extend `safe_bloc`'s `Cubit` (swallows emits after close) and mix in `AutoSubscriptionMixin` (cancels tracked subscriptions before `close()`) for any external stream subscription.

- **External Source Reader Selectors Drift with Site Redesigns**
  - **Location**: `module/domain/domain_manga/assets/sources/` (e.g. `asura-scans.js`, tests in `script_test/asura-scans.test.mjs`)
  - **Context**: AsuraScans (and other scraped sources) rebuilt their site on Astro; the chapter reader DOM changed from `div.relative.w-full > img.w-full.block.relative.z-10` to `<div data-page="n" class="w-full"><img data-page-index="n" class="w-full block">`. The old hardcoded Tailwind-class chain matched **0** images, so the reader silently showed no/incomplete pages while the web version showed all.
  - **Troubleshooting**: Symptom "app reader has fewer/missing images than the site" → the script's `images` function selector is stale. Fetch a live chapter page (`curl -A '<mobile UA>' https://asurascans.com/comics/<slug>/chapter/<n>`), inspect the reader `<img>` attributes, and update the script (in the app: Sources → the source → editor → Test, or edit `assets/sources/*.js` and the Node fixture). Prefer stable attributes (`data-page-index`, `data-page`) over Tailwind classes — they survive redesigns. The `images` function scrolls each `<img>` into view (`scrollIntoView`, then `ctx.sleep`) to trigger lazy `src` population and starts with `ctx.waitFor(selector, <header timeouts.images>)`; keep that timing in sync with the container it queries.

- **Empty-Query Browse URLs Render Empty Pages in the App Webview**
  - **Location**: `module/domain/domain_manga/assets/sources/` (e.g. `manga-katana.js`, `manhua-plus.js`; `searchUrl` in each)
  - **Context**: Scraped sources' `searchUrl` (formerly `searchMangaUseCase.url()`) built the site's *search* URL with the empty browse query. Manga Katana `?search=&search_by=m_name` renders "Not found any results" in `#book_list`, and its <768px inline JS empties the `#hot_book` sidebar widget (repopulated only from `#hot_update`, which exists solely on the homepage), leaving **0** `div.item[data-id]` cards in the post-JS DOM. Manhua Plus `?s=` renders WordPress's "You searched for" page with **0** cards. Curl-only checks are misleading because the raw HTML still contains sidebar widgets that the app's rendered DOM drops.
  - **Troubleshooting**: Symptom "browse shows no cards but search works" → check the script's `searchUrl` for empty-title handling; browse must hit a real listing (homepage/archive), not the search route. Verify with a JS-enabled render (e.g. headless Chrome `--dump-dom` with the app webview UA) rather than curl alone, because the headless webview snapshots the post-JS DOM.

- **Cloudflare JS Challenge Blocks Browse for Some Scraped Sources**
  - **Location**: `module/core/core_network/lib/src/manager/headless_webview_manager.dart` + `module/domain/domain_manga/assets/sources/`
  - **Context**: Some sites (e.g. Toonily) put their homepage and any `/?s=` search behind a Cloudflare "Just a moment…" JavaScript challenge. Detail pages pass, but browse/search are unusable: the webview aborts when `getTitle()` == `'Just a moment...'` (`headless_webview_manager.dart:385`). No User-Agent tweak passes it; `curl` sees the challenge for search but not detail. Toonily was removed as a source (2026-08-11).
  - **Troubleshooting**: Before adding a scraped source, curl its homepage + a search URL with the canonical probe UA: the real platform webview UA at runtime (discovered via `HeadlessWebviewManager` → `UserAgentManager.publish`, `user_agent_manager.dart:25`); the static desktop fallback (`Chrome/154.0.0.0` — see `user_agent_mixin.dart`) applies only pre-discovery/on web. If you see `<title>Just a moment...</title>`, the source cannot browse; remove it or find a non-challenged listing endpoint (some sites only challenge search, not genre/archive pages).

- **Next.js/SSG Sites Parse from `__NEXT_DATA__` JSON, Not the DOM — SOURCE REMOVED**
  - **Location**: technique; last implementation was `flame_comics_source_external.dart` (removed 2026-10, issue #166)
  - **Context**: Flame Comics migrated from Madara WordPress to a Next.js/Mantine SPA (2026-08); on 2026-10-04 the site turned out to be **gone** — `flamecomics.xyz` (apex, `www`) and `flamecomics.com` all 302 to a Discord invite, `cdn.flamecomics.xyz` is dead, `.org` is a parked scam survey — so the source (and its tests) was deleted from `sources.dart`. **Isekai Scans was removed the same day**: `isekaiscans.org` returns HTTP 522 (Cloudflare: origin connection timed out) on every route. Restore either from git history only after verifying the site is live again (curl home + a search URL with the app webview UA). The SSG parsing technique remains valid: browse/search → `props.pageProps.series[]`, detail → `props.pageProps.series` + `pageProps.chapters[]`, reader → `props.pageProps.chapter.images` (dict `"0" → {name, …}`), covers → `https://cdn.flamecomics.xyz/uploads/images/series/{series_id}/{cover}?t={last_edit}`.
  - **Troubleshooting**: For any source whose markup is a Next.js SPA, fetch the page and parse `#__NEXT_DATA__` JSON instead of the DOM — it's stable and complete, and needs **no injected scripts**. Two gotchas: (1) the `html` package does NOT decode HTML entities inside `<script>` text — titles with apostrophes arrive raw (`The Novel's Extra`, not `&#x27;`); (2) when the site's search is client-side only (Fuse.js over the full SSG list), there is no server endpoint — filter the embedded series array in Dart using the `searchTerm` threaded through `SearchMangaSourceExternalUseCase.parse` (add the optional param to the interface + caller).

- **Bumping a Constraint That Intersects a Git-Pinned Dep Requires a Lockfile Commit**
  - **Location**: all committed `pubspec.lock` files (17 at root + every module except `ui_updates` and `feature_common`, whose `.gitignore` excludes their lockfiles)
  - **Context**: `core_analytics` (and several modules) depend on `log_box_*` packages via git with `ref: master`. `flutter pub get` (what `melos get` runs) **reuses the `resolved-ref` pinned in pubspec.lock and never floats a git dep to the branch tip** — only `pub upgrade <pkg>` does. So when commit 18e6558d bumped `rxdart` to `^0.28.0` in pubspec.yamls without regenerating lockfiles, CI's `melos get` kept resolving log_box at the pinned commit `550868b` (still `rxdart ^0.27.7`) and version solving failed with "every version of X from path depends on log_box_dio_logger from git which depends on rxdart ^0.27.7" — even though log_box master already had `^0.28.0`. The resolver's error message tells you which commit it looked at: if it names `^0.27.7`, it read the pin, not the tip.
  - **Troubleshooting**: After changing any constraint that touches a git-pinned dependency, run `flutter pub upgrade log_box log_box_navigation_logger log_box_dio_logger log_box_in_app_webview_logger log_box_persistent_storage_drift` at root and in every module whose lockfile pins the old ref (or full `melos run upgrade`), verify no lockfile still contains the stale `resolved-ref`, then **commit the updated lockfiles together with the pubspec.yaml bump**. `melos run get` alone cannot fix it.
  - **Update (2026-10-10, log_box v0.1.0)**: log_box no longer floats on `master`. Its v0.1.0 release moved core to the repo root (no `path:`) and split the four extensions into standalone repos (`github.com/robzimpulse/log_box_<ext>.git`, tagged `v0.0.1`), each of which pins core at exactly `ref: v0.1.0`. `core_analytics` and `manga_service_drift` now pin those tags. To bump: edit the `ref:` values in both pubspecs — keep core's ref identical to the one every extension's own pubspec pins, or pub cannot resolve two refs of the same git package — then `melos bootstrap` and commit every regenerated lockfile with the pubspec change.

- **Widget Tests Against ScaffoldScreen Cannot Use pumpAndSettle — and a Single Long pump Is Not Enough**
  - **Location**: `module/ui/ui_common/lib/src/scaffold_screen.dart` (ShimmerAreaWidget) + any `ui_*` screen test
  - **Context**: `ScaffoldScreen` embeds an infinitely-animating shimmer, so `WidgetTester.pumpAndSettle` always times out. Replacing it with one long `pump(Duration)` is also wrong: `pump` advances the fake clock and paints a single frame, and `ExpansionTile`/`AnimatedCrossFade` schedule their post-completion rebuild for the *next* frame — the tree is left mid-transition with both layers stacked, and taps then hit the wrong render object ("tap() with finder ... would not hit test"). First observed in the data_storage_screen widget tests (2026-09).
  - **Troubleshooting**: Use a loop helper (e.g. `pumpFrames` = several `pump(200ms)` iterations) after every interaction (tile expansion, popup menu, snackbar). See `module/ui/ui_more/test/src/data_storage_screen/data_storage_screen_test.dart`.

- **Mocking Extension Getters on LogBox Produces Wrong-Reason-Green Tests**
  - **Location**: `module/core/core_network/test/manager/headless_webview_manager_test.dart` + `log_box_in_app_webview_logger`'s `InAppWebviewLoggerExtension`
  - **Context**: `HeadlessWebviewManager._fetch` resolves its observer via `_log.inAppWebviewObserver`, which is an **extension getter** on `LogBox` (from `log_box_in_app_webview_logger`) that constructs `InAppWebviewObserver(storage: storage)` on every call. Extensions are not mock-dispatched: `when(() => log.inAppWebviewObserver).thenReturn(...)` does NOT stub the getter — mocktail's `when` captures the *last mock invocation inside the expression*, which is `log.storage`, so the call silently overwrites the storage stub with the observer object. The observer is then built over a non-`Storage` mock, `observer.set` throws during `_fetch`'s first line, the awaited code under test dies before the interesting call, and negative assertions (`verifyNever`) pass for the wrong reason. First observed in the #145 review-fix test (2026-09).
  - **Troubleshooting**: Never stub `inAppWebviewObserver` — the extension builds a real observer from the already-stubbed `log.storage`, and unstubbed `void` members (`Storage.add`) are recorded harmlessly by mocktail. When a `verifyNever`-style test passes immediately, suspect a wrong-reason green: check that the code path actually reached the interaction before concluding the behavior is absent.

- **drift_flutter Typing and path_provider Quirks in IO Adapters and VM Tests**
  - **Location**: `module/library/manga_service_drift/lib/src/database/adapter/query_executor/` + tests under `test/database/`
  - **Context**: drift_flutter 0.2.x deliberately types `DriftNativeOptions.databaseDirectory` as `Future<Object> Function()` so the same options class compiles for web — on IO adapters you must cast the resolved value to `dart:io` `Directory` (drift uses dart:io's Directory, NOT package:file's). Additionally `driftDatabase` resolves sqlite3's temp dir via path_provider (`getTemporaryDirectory`) unless `tempDirectoryPath` is supplied, and defaults to `shareAcrossIsolates` — both break plain `flutter_test` VM runs with "Binding has not yet been initialized" or MissingPluginException.
  - **Troubleshooting**: In tests that exercise `queryExecutor`/`driftDatabase` directly, pass `DriftNativeOptions(databaseDirectory: () async => Directory(tmp), tempDirectoryPath: () async => tmp, shareAcrossIsolates: false)`. In adapter code, cast `await ioOptions.databaseDirectory?.call() as Directory?`.

- **Web Filesystem Adapters Are Persistent via `persistent_file_system` (fs_shim/IndexedDB)**
  - **Location**: `module/library/persistent_file_system/` + the two web adapters (`module/library/manga_service_drift/lib/src/database/adapter/filesystem/filesystem_web.dart`, `module/core/core_storage/lib/src/manager/path_manager/adapter/filesystem_web.dart`)
  - **Context**: issue #104 — both web adapters used `MemoryFileSystem` (drift's built a fresh one per call), so `FileDao` rows were dead on arrival and backups vanished on reload. They now return fixed roots (`/database`, `/local`) of the shared `persistentFileSystem` singleton (`FsShimFileSystem` over fs_shim's `fileSystemWeb`, i.e. IndexedDB; pure-Dart `newFileSystemMemory()` backs the tests and exercises the same `FileSystemIdb` code path). The wrapper implements the full `package:file` surface; **sync members, links, watch, `File.open()` (RandomAccessFile), and `createTemp` throw `UnsupportedError`** (fs_shim is async-only); fs_shim errors are rethrown as dart:io `FileSystemException` so consumers keep catching one type.
  - **Troubleshooting**: Web file bugs → check both adapters still share the `persistentFileSystem` singleton (two instances = two IndexedDB connections). Browser-quota exhaustion surfaces as `FileSystemException`. Multi-tab writes are last-write-wins (no coordination). Never use `*Sync` members or `File.open()` on these roots. fs_shim is constrained `^2.4.0` because ≥2.4.0+1 required Dart ≥3.9 while the SDK was 3.8.1; since the Flutter 3.47.8 bump (Dart 3.13.7, 2026-10-26) 2.5.x is allowed, but the lockfile still pins 2.4.0 until someone runs `pub upgrade fs_shim` (interface verified identical). Image-cache persistence on web is still unsupported (flutter_cache_manager's web `Config` defaults to in-memory `MemoryCacheSystem` + `NonStoringObjectProvider`) — `Config(fileSystem:)` is the future injection point for that.
- **CustomCacheStore Is a Fork of Upstream CacheStore — Eviction Is Rescue-then-Delete**
  - **Location**: `module/core/core_storage/lib/src/manager/custom_cache_manager/custom_cache_store.dart`
  - **Context**: `CustomCacheStore` forks flutter_cache_manager's `CacheStore`. Upstream deletes evicted files inline in `_removeCachedFile`; this fork runs an awaited `rescueEvictedFile` hook **before** deleting (both failures logged and swallowed) — every evicted file ends up deleted, no branch on a flag (issue #103: rows were deleted but files leaked forever for every cache). `ImagesCacheManager` is the sole hook user: the rescue copies to `FileDao.addFromFile` so evicted images are persisted into the app DB; the old `deleteFileEvent` → `JobManager` `persistentImage` job pipeline was removed. `_cleanupCache`/`emptyCache` await file deletions **before** `provider.deleteAll` (deliberate divergence from upstream) so a crash cannot orphan files with no index rows.
  - **Troubleshooting**: If evicted images stop appearing in the DB, check the `rescueEvictedFile` closure passed by `ImagesCacheManager`. If a cache leaks files on eviction, ensure the eviction paths go through `_removeCachedFile` (all three do: `removeCachedFile`, `emptyCache`, scheduled cleanup). If eviction tests hang, remember `_scheduleCleanup` arms a real timer — drive it with `fakeAsync` + `flushTimers` and `cleanupRunMinInterval = Duration.zero`. Also, mocktail needs `registerFallbackValue` for `Duration` and `CacheObject` when stubbing with `any()`.

- **Schema v3 Enforces Foreign Keys with ON DELETE CASCADE (#137)**
  - **Location**: `module/library/manga_service_drift/lib/src/tables/*` + `database.dart` (`beforeOpen`, `from2To3`)
  - **Context**: since 2026-09-23 the child tables carry real FKs (`chapter_tables.manga_id → manga_tables.id`, `image_tables.chapter_id → chapter_tables.id`, `library_tables.manga_id`, `relationship_tables.(tag_id, manga_id)`) with `ON DELETE CASCADE`, and `beforeOpen` runs `PRAGMA foreign_keys = ON` (per-connection, covers IO and the wasm/IndexedDB web executor). `manga_id` on chapters stays nullable — chapters without a manga are legal (legacy syncs). The v2→v3 migration first deletes legacy orphans (dirty pre-#136 installs) then rebuilds the four tables via `m.alterTable(TableMigration(...))` because SQLite cannot ALTER-add constraints. DAO cascade simplification: `MangaDao.remove`/`ChapterDao.remove` no longer hand-delete children — the DB cascades them — but they must **collect child rows (for file_tables cleanup) before the parent delete**, since cascades make them unreadable afterwards. `file_tables` is webUrl-keyed with no FK and stays app-managed.
  - **Troubleshooting**: `SqliteException(787) FOREIGN KEY constraint failed` on insert ⇒ the fixture/flow wrote a child before its parent — audit ordering (all current sync flows are parent-first). - **Android: A Runaway Script Wedges the Shared WebView Renderer — Only `WebViewRenderProcess.terminate()` Frees It (#115)**
  - **Location**: `module/core/core_network/lib/src/manager/headless_webview_manager.dart` (`_terminateRenderer`) + `android/app/src/main/kotlin/com/robzimpulse/mangastash/MainActivity.kt` (`webview_renderer` channel)

Any NEW call site of `logBox.webview(...)` MUST be wrapped in `guard.track`.
